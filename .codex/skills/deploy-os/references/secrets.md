# Секретный контур

`secretsctl --root /path/to/private-state` использует каталог выбранного
приватного checkout. SOPS получает ключи стандартным способом; toolkit не
добавляет учётную запись Keychain или отдельного получателя.

- `validate` проверяет схему, контейнеры и отсутствие открытых значений;
- `list`, `show ID` возвращают metadata;
- `import ID --from URI` и `sync ID --to URI` сначала выполняют dry-run;
- `--apply` разрешает запись; `import --replace` явно выбирает новый источник;
- `check ID` возвращает match/mismatch/unavailable;
- `backup MIRROR --apply` и `check-mirrors` проверяют полную Git-копию.

Поддержаны file, workspace-file и ssh-file. Workspace root по умолчанию —
родитель private state; явная настройка — `DEPLOY_OS_WORKSPACE_ROOT`.
Для SSH нужны приватные `hosts/<alias>.env`, BatchMode и доверенный host key.
Другие схемы отклоняются. Docker, Kubernetes и Keychain требуют отдельного
адаптера и соответствующих проверок перед подключением.

Права локальной реплики сохраняются при замене существующего файла. Новые
файлы создаются с 0600. SSH sync требует существующий файл, сохраняет его права
и владельца. В каталоге writable разрешается только для реплик, которыми
управляет эта процедура. Параллельные записи одного секрета сериализуются
операционным процессом.

Никогда не печатать расшифрованные значения, stdout/stderr SOPS, токены или
содержимое runtime-конфигурации. Ошибки инструмента дают причину и безопасный
следующий шаг. После неясного исхода записи сначала проверить фактическое
состояние и затем принимать решение о повторе.
