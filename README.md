# Deploy OS

Deploy OS помогает вести инфраструктуру как воспроизводимый процесс: знать,
где работает приложение, какой выпуск установлен, где лежит резервная копия и
как восстановить сервис. Общие команды и навык для агента связывают эти шаги
с исходниками приложения и вашим приватным описанием инфраструктуры.

Типичный сценарий: у вас есть приложение и VPS. Вы с агентом описываете хост,
способ выкладки, backup и rollback в приватном репозитории. После этого
`vps-ops plan` вызывает план нужного проекта, а следующие операции используют
тот же профиль; результаты фиксируются в приватной документации и Git по
процессу проекта.

## Как связаны три репозитория

| Репозиторий | Что в нём хранится | Пример локального имени |
| --- | --- | --- |
| Публичный набор инструментов (toolkit) — этот репозиторий | Общие команды, единый навык `deploy-os`, тесты и синтетические примеры | `deploy-os` |
| Ваш приватный репозиторий состояния (state) | Инвентарь, хосты, проектные профили, инструкции, каталог секретов, зашифрованные копии и восстановление | `my-infrastructure` |
| Исходники приложения | Код продукта, его тесты и маркер связи `.ops-project` | `my-app` |

`DEPLOY_OS_ROOT` всегда указывает на **приватный репозиторий состояния**.
Путь к набору инструментов нужен для запуска общих команд; путь к приложению
передаёт его исходники. Один стабильный `project_id` в `.ops-project` связывает
приложение с записями и профилем в приватном состоянии.

Реальные сведения об инфраструктуре хранятся в вашем приватном репозитории.
Это относится и к зашифрованным `vault/` и `recovery/`: их содержимое и история
остаются приватными. В публичный набор входят только общий код и примеры.

## Что делают инструменты

| Инструмент | Назначение |
| --- | --- |
| Навык `$deploy-os` | Помогает агенту создать или восстановить приватное состояние, подключить проект и выполнить операции по его инструкциям |
| `vps-ops` | Находит `.ops-project` и запускает `private-state/projects/<id>/operations.sh` с выбранным действием; конкретные команды выкладки задаёт этот профиль |
| `secretsctl` | Работает с каталогом и SOPS-копиями приватного состояния: проверяет, импортирует и синхронизирует зарегистрированные реплики, проверяет резервные Git-копии |
| `install-deploy-os` | Устанавливает инструменты по полному commit в отдельный каталог, ведёт запись версии и операции update, rollback, recover |
| `bootstrap-deploy-os` | Подключает установленный навык и команды ссылками к выбранному пользовательскому каталогу; проверяет коллизии перед записью |

Приватный репозиторий состояния и его первый профиль создаются с агентом
или вручную по
[сценарию первого запуска](.codex/skills/deploy-os/references/create-state.md).
Для каждого приложения в профиле определяются его реальные deploy, smoke и
rollback. Проверка примеров подтверждает локальные контракты; работу сервиса
на хосте принимают отдельно после backup и разрешённой выкладки.

## 1. Подготовьте окружение

Для команд нужны Python 3.11+, Git и POSIX shell на Linux или macOS.
Для операций с зашифрованными секретами установите
[SOPS](https://getsops.io/docs/) и [age](https://age-encryption.org/) и настройте
собственные ключи. Локальный пример ниже, включая `secretsctl list`, работает
без SOPS, age и доступа к VPS.

## 2. Попробуйте безопасный локальный пример

```sh
git clone https://github.com/z0rgoyok/deploy-os.git
cd deploy-os
TOOLKIT="$PWD"
export DEPLOY_OS_ROOT="$TOOLKIT/examples/state"

"$TOOLKIT/bin/vps-ops" --source "$TOOLKIT/examples/application" plan
"$TOOLKIT/bin/secretsctl" list
unset DEPLOY_OS_ROOT
```

Ожидаемый результат:

```text
Synthetic plan: inspect application source and verify its project marker.
Каталог секретов пока пуст.
```

Это синтетический профиль внутри набора инструментов: команды читают локальный
пример и не обращаются к серверам. В рабочей системе состояние инфраструктуры
и приложение имеют отдельные репозитории. Последняя команда снимает пробную привязку `DEPLOY_OS_ROOT`;
переменная `TOOLKIT` сохраняется для следующих шагов.

## 3. Установите проверенный выпуск изолированно

Выберите полный SHA принятого выпуска. Ниже закреплён выпуск с единым навыком:

```sh
TOOLKIT_COMMIT=3a4139c7f68a7850dad8013b892f5dc5c7aa2da8
PREFIX="$HOME/.local/share/deploy-os-toolkit"

"$TOOLKIT/bin/install-deploy-os" install \
  --prefix "$PREFIX" \
  --expected-origin https://github.com/z0rgoyok/deploy-os.git \
  --commit "$TOOLKIT_COMMIT"

ISOLATED_HOME="$PREFIX/home"
export PATH="$ISOLATED_HOME/.local/bin:$PATH"
```

Установка сохраняет код в `PREFIX/releases/<commit>`, активную ссылку
`PREFIX/current`, запись `PREFIX/install.json` и ссылки команд и навыка внутри
`PREFIX/home`. Изменение PATH действует в текущем shell. Пользовательский
каталог навыков и shell-конфигурация этим шагом не меняются.

## 4. Подключите навык к агенту и создайте приватное состояние

Изолированный `PREFIX/home` сам по себе не добавляет навык в каталог вашего
агента. Можно передать агенту путь
`<prefix>/current/.codex/skills/deploy-os/SKILL.md` и попросить прочитать его.

Для подключения к пользовательскому каталогу Codex выполните отдельный явный
шаг. Он создаёт ссылки в `$HOME/.codex/skills` и `$HOME/.local/bin`:

```sh
DEPLOY_OS_INSTALL_HOME="$HOME" "$PREFIX/current/bin/bootstrap-deploy-os"
```

Bootstrap подключает один навык и останавливается при коллизиях с чужими
путями. Ссылки этого шага закреплены за конкретным установленным выпуском;
последующий update изолированного prefix требует отдельной проверки и
осознанного переподключения пользовательских ссылок. При работе через явный
путь `PREFIX/current` агент может читать активную версию навыка.

Пример запроса агенту после подключения навыка:

> Используй $deploy-os. Подготовь приватный репозиторий my-infrastructure для
> моего приложения my-app. Сначала найди существующее авторитетное состояние
> и резервные копии. Область работы — локальные репозитории. Подготовь
> инструкции, связь проекта и профиль с безопасным plan, затем покажи результат.

Агент уточнит реальные пути и первое приложение. Если приватное состояние
уже существует, он использует его проверяемый источник. Отсутствие `DEPLOY_OS_ROOT` требует
выбрать правильный репозиторий; создание отдельной системы задаётся вашим запросом.

## 5. Подключите первый проект

После подготовки приватного состояния задайте его путь и путь существующего
Git-репозитория приложения:

```sh
STATE="$HOME/dev/my-infrastructure"
APPLICATION="$HOME/dev/my-app"
export DEPLOY_OS_ROOT="$STATE"
```

В корне приложения нужен `.ops-project` со стабильным идентификатором:

```text
project=my-app
contract_version=1
```

Тот же `my-app` регистрируется в приватном состоянии. Для приложения
с выкладкой агент готовит `STATE/projects/my-app/operations.sh`, где реализован безопасный plan
и остальные необходимые действия. Затем из приложения можно вызвать:

```sh
cd "$APPLICATION"
vps-ops plan
```

`vps-ops` находит маркер до границы Git-репозитория и передаёт управление этому
приватному профилю. Дальнейшие inspect, backup, deploy, smoke и rollback
выполняются по его контракту. Для одного вызова `secretsctl --root "$STATE" list`
может явно выбрать репозиторий состояния вместо `DEPLOY_OS_ROOT`.
